## Why

The explainer page was already migrated from hand-authored HTML to a compiled Markdown source (`explainer.md`) using `marked`, on the reasoning that `marked` is the lighter dependency for a single file and passes raw embedded HTML straight through unmodified. That migration is complete and shipped.

In practice, `marked`'s raw-HTML-passthrough model has a real cost: it treats any `<div>`/`<figure>`/`<figcaption>` as an opaque block, so their contents never get Markdown-parsed — `<a>`, `<code>`, `<strong>` inside `.callout`, `.lede`, and every figure caption have to stay literal HTML, and `<span class="math">` sitting in flowing prose needs a token-protection workaround to survive CommonMark's own backslash-escape rule stripping `\(`, `\{`, etc. The source is still more HTML than the original migration intended.

Separately, the page's MathJax setup is hand-wired: a pinned CDN script, an inline config block, and a `math-pending` CSS class toggled by script to hide un-typeset TeX during load. Building this through `remark-math` + `rehype-mathjax` in `browser` mode lets the same toolchain that authors the prose also generate this wiring, instead of it being separately hand-maintained HTML in the shell.

This proposal supersedes the `marked`-based implementation with a `remark`/`unified`-based one, adding a `::: classname` directive syntax so containers can hold real Markdown, and moving math source syntax to GFM-style `$...$`/`$$...$$`. It accepts a MathJax version downgrade (from the `@mathjax/src` v4 line to whatever version `rehype-mathjax`'s `mathjax-full` v3 peer dependency requires), since `rehype-mathjax` has no known v4-compatible release.

## What Changes

- **Compiler engine**: `compileExplainer()` moves from a single `marked.parse()` call to a `unified()` pipeline: `remark-parse` → `remark-directive` → `remark-math` → `remark-rehype` (with `allowDangerousHtml: true` for the figure/demo-widget markup that still can't be expressed as a directive) → `rehype-raw` → `rehype-mathjax/browser` → `rehype-stringify`. `computeFigureValues()`/`substituteFigures()` (the `data-figure` injection) stay unchanged, applied as post-processing on the final HTML string.
- **Directive syntax, scoped to where it earns its dependency**: `remark-directive` only parses `:::`/`::`/`:` syntax — it doesn't decide what HTML a directive becomes, so a hand-written mapping is required regardless of scope. That mapping now covers exactly what benefits from real nested-content parsing:
  - **Figures**: `::: figure ... :::` (with a nested `::: figcaption ... :::`) replaces the current `<figure>`/`<figcaption>` raw HTML, letting caption prose use real Markdown (`<a>`, `` ` ` ``, `**...**`) while the `<img>` tags (and, for the two-image figures, their wrapper divs) stay as raw HTML inside the directive body via `rehype-raw`.
  - **Term spans**: `:term-safe[...]`, `:term-mine[...]`, `:term-clue[...]`, `:term-premise[...]` (inline text directives) replace the current raw `<span class="term-*">` spans — zero added cost since the directive plugin is already required for figures.
  - **`.callout`** moves to GFM-style alert syntax (`> [!NOTE] ...`) via `remark-github-markdown-alerts`, configured with custom `classNames`/`tags` so it emits the existing `.callout` markup rather than GitHub's own alert styling — no `remark-directive` involvement, and no `remark-gfm` dependency needed (GitHub alerts are a GitHub convention layered on GFM blockquotes, not the core GFM spec).
  - **`.lede`** is dropped as a class entirely; the stylesheet targets it structurally (the paragraph immediately following `<h1>`) instead. No markdown-side syntax change at all.
  - The interactive demo widget (`<canvas>`/`<dl>`/`<button>`) remains raw embedded HTML — out of scope, its structure doesn't reduce to a directive with useful semantics.
- **Math source syntax**: every `<span class="math">\(...\)</span>` and `<div class="math-display">\[...\]</div>` in `explainer.md` becomes `$...$` / `$$...$$`, parsed by `remark-math` and rendered via `rehype-mathjax/browser`. This mode does not typeset at build time — it still relies on a client-side MathJax runtime, matching today's architecture, but the specific script/config wiring in `explainer.html`'s shell is generated by the toolchain rather than hand-maintained, and the MathJax major version served changes from v4 to whatever `rehype-mathjax`'s current `mathjax-full` (v3 line) peer dependency requires. The rendered formulas are expected to look the same; this is a toolchain version change, not an intentional visual change.
- **Dependencies**: add `unified`, `remark-parse`, `remark-directive`, `remark-math`, `remark-rehype`, `rehype-raw`, `rehype-mathjax`, `rehype-stringify`, `unist-util-visit` (for the directive-to-hast mapping plugin), and `remark-github-markdown-alerts` (for the `.callout` alert). Remove `marked`. Remove `@mathjax/src` if `mathSyntax.test.ts`'s standalone TeX-validation approach can be retired in favor of relying on the real build pipeline surfacing bad TeX (see design.md); keep it if that check is kept as a belt-and-suspenders test.
- **Shell (`explainer.html`)**: the MathJax CDN script, integrity hash, inline config block, and `math-pending` class are re-derived from whatever `rehype-mathjax/browser` actually emits — exact shape is TBD pending implementation-time verification of the current `rehype-mathjax` API (do not assume the prior hand-written config carries over unchanged).
- **Tests**: `explainerPage.test.ts`'s MathJax-loading assertions (script tag, SRI hash, config ordering, `math-pending` fallback) are re-pointed at whatever the new pipeline actually emits, which may differ in shape from the current hand-authored config. `mathSyntax.test.ts` is revisited — either kept as a standalone TeX-validation check against the new math source, or retired if the build pipeline itself makes bad TeX visible. `figures.test.ts` and `illustrationFiles.test.ts` continue to exercise `compileExplainer()`'s output as they do today; no change to their approach.
- **BREAKING** (internal only): the exact HTML `rehype-mathjax/browser` produces for math, and the MathJax version/config shipped to the browser, may differ in specific markup/version from today's hand-authored setup even though the intent is unchanged rendering. Nothing else user-facing changes: figures, the certainty highlighting, and the predicted-vs-realized demo are unaffected.

## Capabilities

No spec-level behavior changes: the explainer's observable content, structure, and interactivity are unchanged (see `openspec/changes/add-explainer-page/specs/explainer/spec.md`) — only how the page is authored, compiled, and how math is wired up. This change sets `skip_specs: true`.

## Impact

- `explainer.md` rewritten to use `> [!NOTE]` GFM alert syntax for the callout, `::: figure`/`::: figcaption` container directives for every figure, `:term-safe[...]`-style inline directives for term spans, and `$...$`/`$$...$$` math syntax, in place of the current embedded HTML wrappers for those elements. The `.lede` class is dropped (retargeted via CSS structural selector). The demo widget block is unchanged (still raw embedded HTML).
- `src/explainer/compileExplainer.ts` rewritten around a `unified()` pipeline instead of `marked`; adds a directive-to-hast mapping plugin scoped to `figure`/`figcaption`/`term-*`, plus `remark-github-markdown-alerts` configured to emit `.callout`'s existing markup.
- `vite.config.ts`'s explainer-compiling plugin is unaffected (still just calls `compileExplainer()`).
- `explainer.html`'s shell `<head>` MathJax wiring is regenerated/re-verified against `rehype-mathjax/browser`'s actual current output; the `.lede` CSS rule is retargeted to a structural selector.
- `package.json`: add the `remark`/`rehype` packages listed above; remove `marked`; possibly remove `@mathjax/src`.
- Updated: `src/explainer/explainerPage.test.ts` (MathJax assertions revisited), `src/explainer/mathSyntax.test.ts` (revisited or retired), `src/explainer/compileExplainer.test.ts` (internals change, external contract doesn't).
- No change to `src/explainer/main.ts`, `revealDemo.ts`, `worldsTree.ts`, `illustrations.ts`, `figures.test.ts`, `illustrationFiles.test.ts`'s approach, or any solver/runtime code; no change to the live game.
