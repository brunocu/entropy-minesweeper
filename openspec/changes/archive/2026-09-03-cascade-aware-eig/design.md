## Context

See proposal.md - Why. Current EIG (`computeFrontierCellResult` in `src/solver/frontierSolver.ts:623-677`) is exact but single-reveal: it treats a cell's "safe:0" outcome as just another bucket in the outcome-partitioned entropy calculation, with no credit for the flood-fill cascade a real 0-reveal triggers in `board.ts`'s `floodReveal` (`src/board/board.ts:137-152`).

The solver's existing tractability rests on *not* enumerating individual shadow-cell (non-frontier) mine placements — `solve()` only tracks aggregate counts via `binomial(K, remaining)`. A cascade's reach depends on the exact spatial placement of mines in that shadow region, which the aggregate representation doesn't have. Recovering that exactly (full re-enumeration, or a re-solve conditioned on a hypothetical cascade's revealed set) reintroduces the combinatorial cost the aggregation was designed to avoid. This design deliberately does not attempt that; it estimates instead.

**Literature check (session research, 2026-09-03):** entropy/EIG-of-enumerated-worlds move selection is an established approach in the Minesweeper-solver literature (e.g. Studholme's CSP formulation, Sheppard's 2023 entropy-based solver) — this design's core is not a novel or fringe framing. Both research threads independently found **no prior published work addressing the single-reveal-vs-cascade EIG gap this change targets** — it appears to be a genuinely unaddressed gap, not a known problem with an established solution being reinvented poorly. See Risks/Trade-offs for where the literature also surfaced sharper concerns about the specific approximation chosen.

## Goals / Non-Goals

**Goals:**
- Add a cascade-aware term to `eig` that is O(cascade footprint) per frontier cell — no sampling, no re-solve, no combinatorial enumeration of shadow-cell placements.
- Use exact information already available for free (each frontier cell's real solver probability, each cell's true unrevealed-neighbor count including board-edge/corner and already-revealed-region effects) wherever it's cheap to do so, falling back to a density estimate only where nothing better exists.
- Keep the existing exact probability/EIG machinery (Trivial Deduction, Component Decomposition, Joint World Enumeration, Global Mine-Count Weighting) completely unchanged.

**Non-Goals:**
- Exact cascade-aware EIG. Not attempted — establishing why it's intractable at this scale was the point of the exploration that preceded this change.
- Detecting when a cascade would reconnect two separate frontier components and resolve one via the other. Explicitly out of scope (see Risks/Trade-offs) — doing so requires a conditional re-solve.
- Any change to `board.ts`'s actual reveal/cascade gameplay logic. This only affects the solver's *prediction*.

## Decisions

### 1. Composition: additive, not a replacement

`EIG_cascade(x) = EIG_single(x) + sum over n in CascadeBFS(x), n != x of p(n) * H(n)`

`EIG_single(x)` is today's unchanged exact computation. The cascade term is purely additive so the exact core is never disturbed by the estimate — if the BFS term were ever removed or zeroed, behavior reduces exactly to today's solver.

**Alternative considered**: replace `eig` outright with a from-scratch cascade-inclusive entropy calc. Rejected — it would require re-deriving the exact machinery's guarantees for the estimated part too, mixing exact and approximate reasoning in one derivation rather than keeping them separable.

### 2. Cascade reveal-probability: layered BFS propagation, not a scalar branching-process formula

Starting from `p(x) = 1`, propagate outward one BFS layer at a time:

```
q0(cell) = (1 - q)^d(cell)     -- P(cell is itself a "0"), using cell's TRUE
                                   unrevealed-neighbor count d(cell) (3 at a
                                   corner, 5 on an edge, 8 interior, and reduced
                                   further wherever a neighbor is already revealed)

p(n) accumulates p(parent) * zero(parent) from EVERY already-processed
neighbor of n reachable in the previous layer, not just the first
```

`zero(cell)` is "P(cell is a 0)" and is **not** always `q0`: for `x` itself — the root, always a known frontier cell — it's the solver's *exact* `cascadeProbability(x)` (`outcomeProbabilities.get('safe:0')`), not the density estimate. The same substitution applies at every later layer too, whenever the reached cell `n` happens to already be an enumerated frontier cell: use its exact solver-reported probability of being a 0, not `q0(n)`. `q0(cell) = (1-q)^d(cell)` is the fallback, used only where no exact probability exists (genuinely unresolved shadow territory) — it is never the right choice for `x` itself.

`q` is the local mine density: `nonFrontierProbability` from the existing `solve()` result by default.

One consequence worth stating explicitly: because the root always uses the exact `cascadeProbability(x)`, if that's `0` (the solver already knows `x` can't be a 0 — e.g. `x` is forced to be a mine), every `p(n)` downstream is `0 * (anything) = 0`, so `expectedCascadeInfo` evaluates to exactly `0` with no special-casing required. Skipping the BFS entirely in that case is a valid performance shortcut (an implementation detail, not a design decision — belongs in tasks.md).

**Correction (2026-09-03, informed by `cascade-eig-calibration`'s findings): `p(n)` MUST be capped at 1.** As originally written, "`p(n)` accumulates `p(parent) * zero(parent)` from EVERY already-processed neighbor" summed those contributions with no upper bound. Since `p(n)` is a probability, it cannot exceed 1 — but on an open 2D region a cell frequently has several already-processed predecessors, and summing their contributions uncapped let `p(n)` exceed 1 in practice (the calibration harness measured individual reach-node probabilities up to ~1.045, and a reach-wide probability sum of ~160, on an open, low-density interior region). This is not a subtle edge case of the independence assumption — it's a plain correctness bug in a quantity documented as a probability, and it was directly inflating `expectedCascadeInfo` well beyond what even the (already-flagged) independence-assumption overestimate accounts for. The fix: `p(n) = min(1, sum of predecessor contributions)`, applied at the point each layer's contributions are accumulated, so the cap also constrains what a capped node can propagate to the *next* layer (not just the reported value).

Expansion is pruned once `p(cell)` decays below a small threshold (`epsilon`, tunable — see Open Questions), which naturally bounds cost even in a supercritical (large-cascade-likely) region, since real board boundaries and already-revealed regions also cap `d(cell)` and therefore the propagation.

**Alternatives considered:**
- *Scalar branching-process closed form* (`E[cascade size] ≈ 1/(1-mu)` with a single blended `mu`): rejected as the primary mechanism — it can't see real board edges, corners, or already-revealed boundaries without hand-tuned correction terms, and diverges awkwardly in the supercritical case instead of naturally bounding itself.
- *Monte Carlo sampling* (sample concrete mine layouts, flood-fill each, average): rejected — while sampling one layout is cheap (`O(K)`), getting an honest entropy delta per sample requires re-running something solve()-shaped per sample per candidate cell, multiplying cost by `samples x candidates` for comparatively little accuracy gain over the deterministic BFS estimate.

**Literature check (see Risks/Trade-offs for the consolidated finding):** the layered, single-pass "accumulate from every already-processed predecessor" propagation resembles two established techniques, and is weaker than both. It resembles *loopy belief propagation* on a cyclic graph, but real LBP iterates message passing to a (non-guaranteed) fixed point; a single pass is a strictly weaker, bespoke simplification, not a known/established method being reused here. It also resembles the *Independent Cascade model* from network-diffusion/influence-maximization research (Kempe, Kleinberg & Tardos, KDD 2003) — nodes probabilistically activating neighbors, propagating outward — though ours is per-cell-activation-probability (`q0`) rather than IC's per-edge propagation probability. Neither resemblance is a source of validation: no published closed-form or single-pass approximation exists for either technique that this design could be checked against. Full detail in Risks/Trade-offs.

### 3. Per-cell self-entropy `H(n)`

For a shadow cell not otherwise resolved:

```
H(n) = -q*log2(q) - (1-q)*log2(1-q) + (1-q)*H(adjacent-mine-count distribution | non-mine)
```

i.e. the binary entropy of "is `n` a mine" plus the non-mine branch's share of the conditional
number-distribution entropy, via the standard entropy grouping/chain-rule decomposition
(Cover & Thomas, *Elements of Information Theory*, ch. 2.5): partitioning `n`'s outcome space into
{mine} (probability `q`, zero internal entropy) and {safe:0, ..., safe:d} (probability `1-q`,
internal entropy `H(K|non-mine)`) gives `H(n) = H_b(q) + (1-q)*H(K|non-mine)`, where `H_b` is the
binary entropy function. (Corrected 2026-09-04 during apply: the version first written here
dropped the `-(1-q)*log2(1-q)` term and subtracted rather than added the conditional term, which
could make `H(n)` negative and violate this change's own non-negative-cascade-term requirement;
verified against Cover & Thomas and confirmed before fixing.)

where the conditional number distribution is the mean-field estimate `Binomial(d(n), q)` restricted to non-mine, consistent with the same local-independence assumption `q0` already uses. This reuses `q`/`d(n)` with no new solver passes.

### 4. `cascadeProbability` is exposed as a plain field, not derived by the caller

`FrontierCellResult.cascadeProbability = outcomeProbabilities.get('safe:0')`. Already computed exactly today; this just names it, so `revealFeedback.ts` and any UI can show "P(cascade)" without recomputing anything.

## Risks / Trade-offs

- **[Overestimation from independence assumption]** → Summing `p(n)*H(n)` treats each newly-reachable cell's information as independent, but they share the same finite mine budget. This is not a symmetric, direction-unknown risk: it is the standard `H(X)+H(Y) >= H(X,Y)` fact (equality iff independent), and for percolation-style cluster growth specifically, ignoring the negative correlation induced by drawing a fixed mine count without replacement from a finite pool is documented to bias mean-field estimates toward *overestimating* cluster size. So `expectedCascadeInfo` should be expected to run high, not just "off." Not mitigated in this change — accepted, and named explicitly in the proposal rather than left implicit. The planned empirical comparison (below) is how the magnitude gets characterized rather than assumed. **Update (2026-09-03):** `cascade-eig-calibration`'s Part 1 results confirmed positive (overestimating) raw bias in every measured (density, boundary-bucket) cell, consistent with this prediction — but also surfaced a separate, larger-magnitude bug (uncapped `p(n)` exceeding 1, see Decision 2's correction) that was compounding this expected bias well beyond what the independence assumption alone predicts. The `p(n)` cap fixes the compounding; the underlying independence-assumption overestimate remains, unmitigated, as originally scoped here.
- **[Grid/short-cycle structure is a known adversarial case for this whole class of approximation — triangulated finding]** → Three independent bodies of literature (session research, 2026-09-03), consulted separately, converge on the same structural conclusion: percolation theory finds mean-field cluster-size estimates least reliable near the percolation transition (relevant here — see the density-regime risk below); belief-propagation theory names dense-short-cycle graphs (2D grids are the textbook case — every 2x2 block is a 4-cycle) as the classic adversarial input for tree-based message passing, with no convergence guarantee once cycles exist; and independent-cascade/influence-maximization research explicitly names grids' high local clustering (as opposed to the locally tree-like structure of typical social/sparse graphs) as pathological for exactly this "propagate outward, treat neighbors as roughly independent" style of estimate, and reports that computing the *exact* IC-model expected cascade size is #P-hard in general graphs — motivating simulation-based (not closed-form) approaches in that field, with no published one-pass approximation like this design's to validate against, favorably or otherwise. None of these three fields is telling us the estimate is *wrong* — but all three independently point at grid/short-cycle structure, which is exactly this board's structure, as the specific place this class of approximation is weakest. Not mitigated in this change; see the quantification approach under Migration Plan for how this gets measured rather than assumed.
- **[Near-critical density regime]** → Mean-field/independence approximations for percolation-style cluster growth are least reliable near the percolation transition. Moore-neighborhood (8-connected) site percolation on a 2D lattice has a known critical threshold around p_c ~= 0.407 for raw occupation (Random site percolation thresholds on square lattice for complex neighborhoods, ScienceDirect), but the actually-relevant transition for Minesweeper's *mine-free-cluster* problem specifically has been analyzed as occurring around a mine density of ~0.1 (Mossel, "The Minesweeper Game: Percolation and Complexity," Combinatorics, Probability and Computing, 2002). This game's difficulty presets sit at ~12% (beginner), ~16% (intermediate), and ~21% (expert) mine density — plausibly straddling that transition rather than being safely deep in an "always small" or "always huge, capped by the board" regime. This is a materially sharper risk than "the approximation has some error": at these densities the estimate may be least trustworthy exactly where the game is normally played. Not mitigated in this change; flagged as a specific, not merely generic, concern for the planned empirical comparison to check.
- **[Fusion blind spot: a cascade reconnecting into a separate, already-partially-solved frontier component]** → This is the single largest real information jump a cascade can produce, and this design cannot detect it — doing so needs a conditional re-solve, which is the cost this change exists to avoid. Not mitigated. Explicitly called out in proposal.md and here so it isn't rediscovered as a surprise later.
- **[Breaking change to `eig`'s meaning]** → Existing tests asserting single-reveal EIG values will need updating to account for the added term (or to assert against `EIG_single` directly if that's exposed for testing). No runtime migration needed — this is a client-side computation with no persisted state.
- **[Worst-case BFS cost on very open boards]** → probability-threshold pruning should bound this in practice, but it's worth a hard backstop (e.g., a max node count) in addition to the probability epsilon, purely as a safety net — see Open Questions.

**Correction-technique literature review (session research, 2026-09-03, post-`cascade-eig-calibration`):** with real bias numbers in hand (see the "Overestimation from independence assumption" update above), a follow-up review specifically surveyed the literature for a *cheap* correction to the independence-assumption overestimation — something that could stay within roughly O(cascade footprint), i.e. no full re-enumeration, no per-move conditional re-solve, no per-candidate-cell Monte Carlo requiring many `solve()`-shaped re-runs. Five threads were checked in parallel:

- *Percolation pair approximation / cluster expansion* (Matsuda et al., *J. Theoretical Biology* 150(2):243-262, 1992; van Baalen, "Pair Approximations for Different Spatial Geometries," in *The Geometry of Ecological Interactions*, Cambridge, 2000; Levin & Durrett, *Phil. Trans. R. Soc. B* 351:1615-1621, 1996; Sykes & Essam, *J. Math. Phys.* 5(8):1117-1127, 1964) extends mean-field by one order via joint occupied/empty-neighbor pair frequencies — the direct literature answer to "is there a known correction one order beyond mean-field." Every formulation found is a coupled ODE / fixed-point system, not a static per-cell multiplier; correction-to-scaling exponents for 2D percolation (Hu, Mao & Izmailian, *Phys. Lett. A* 375:2811-2815, 2011) are exact but describe the asymptotic cluster-size-distribution tail shape near criticality, not a per-seed adjustment. Not cheap enough.
- *Belief-propagation refinements for short-cycle graphs* (Yedidia, Freeman & Weiss, "Constructing Free-Energy Approximations and Generalized Belief Propagation Algorithms," *IEEE Trans. Info. Theory* 51(7):2282-2312, 2005; Mooij, Kappen & Wemmenhove, *Neural Computation* 19(9):2372-2412, 2007; Chertkov & Chernyak, "Loop series for discrete statistical models on graphs," *J. Stat. Mech.* P06009, 2006) — Bethe/Kikuchi/GBP require iterating a region-graph to convergence, not a single pass. Loop series expansion is the one technique here with a genuinely closed-form per-loop correction term, but summing over even just the grid's native 4-cycles (one per 2x2 block) costs O(grid area) — a second BFS-scale pass, not a constant-factor addition to the first. Damped/normalized message passing (Mooij & Kappen, *J. Stat. Mech.* P11008, 2005) was checked and ruled out specifically: damping addresses oscillation/convergence, not bias — a damped single pass carries the same approximation error as an undamped one.
- *Independent Cascade model corrections* (influence-maximization literature) surfaced one structural fact worth recording precisely: single-round-activation IC is *provably equivalent* to bond percolation (Miller, "Equivalence of several generalized percolation models on networks," *Phys. Rev. E* 94:032313, 2016) — this design's BFS propagation is not merely analogous to both loopy BP and IC (as stated above), it *is* a percolation process, framed in IC's per-node-activation-probability language rather than IC's canonical per-edge language. That sharpens which literature is authoritative (percolation theory) but doesn't unlock a new cheap correction. Tree Distribution Approximation (Burkholz & Quackenbush, AAAI 2021, arXiv:1909.05416) runs in O(nodes+edges) but its own reported failure mode on clustered graphs is underestimating variance/tail multi-modality, not a validated fix for a mean-overestimation bias. Multi-type branching processes for clustered networks (McSweeney, arXiv:1510.00056, 2016; *Phys. Rev. E* 105:034306, 2022) correctly predict that clustering *amplifies* cascade size on grid-like graphs, but require a per-seed fixed-point solve.
- *Correlated/negatively-associated entropy bounds* — the most direct hit on our actual mechanism (shared finite mine budget = negative association among shadow cells), and the cleanest negative result: the hypergeometric-vs-binomial finite-population variance correction `(N-n)/(N-1)` is exactly the "cheap closed-form correction factor" shape hoped for, and Joag-Dev & Proschan's foundational negative-association paper (*Ann. Statist.* 11(1), 1983) proves the covariance/concentration properties that make hypergeometric draws negatively associated — but no source found derives an *entropy* analog of that variance correction. The canonical-vs-grand-canonical ensemble entropy gap (statistical mechanics) is the right conceptual analogy — fixed-N vs. free-N mine placement is literally that distinction — but that gap is a thermodynamic-limit quantity with no known cheap finite-lattice closed form.
- *Existing Minesweeper-solver literature* (Studholme's CSP solver, Kaye's NP-completeness paper, Sheppard's 2023 entropy-based solver, and several open-source solvers) was re-checked specifically for a published cascade-aware/flood-fill-aware EIG estimate with a bias correction — none found. Independent re-confirmation of this design's original finding that the single-reveal-vs-cascade EIG gap is a genuinely unaddressed problem, not a rediscovery.
- *Other candidates surveyed*: clustering-coefficient/motif-density corrections (e.g. "biparallel motifs" in "Critical Network Cascades with Re-excitable nodes," arXiv:1905.07433 — the network-science name for the grid's ubiquitous 4-cycles) are conceptually the cheapest-sounding idea found — motif density around a cell is genuinely O(1) to compute during the same BFS pass — but no source supplies an actual formula; it would need to be fit empirically. Second-order Bonferroni/inclusion-exclusion correction (subtracting pairwise joint-reveal probability between grid-adjacent cells) is architecturally the best-fitting *template* — grid adjacency makes "pairwise overlap with a neighbor" a natural O(1)-per-edge accumulator during the same traversal — but no literature source validates a formula for the pairwise-overlap term itself without already solving the correlation problem it's meant to fix.

**Consolidated finding, matching the shape of every prior literature check in this document:** the rigorous fix for each of pair approximation, GBP/Kikuchi, loop series, and multi-type branching processes for clustered networks is real and well-established — but every one costs strictly more than a single BFS pass (an iterative fixed-point solve, a coupled ODE system, or combinatorial loop enumeration). No field surveyed publishes a free, closed-form, single-pass correction for this exact problem. That negative result is itself worth recording rather than re-discovering later. **Ranked recommendation, if a follow-up change pursues this:** (1) best cost/benefit — an empirically-calibrated local correction (a per-cell/per-edge discount keyed to 4-cycle/motif density, computable in O(1) extra work during the existing BFS traversal), fit against `cascade-eig-calibration`'s harness directly rather than derived from a citation, since no citation supplies the formula anyway; (2) more principled but higher-risk — hand-derive a hypergeometric-style entropy correction by analogy to the finite-population variance-correction shape, verified against the calibration harness rather than trusted a priori, since it targets the actual mechanism (shared finite mine budget) rather than a proxy, but requires original derivation, not literature reuse. Bethe/GBP/Kikuchi, full loop series, pair approximation/general moment closure, and multi-type branching processes are flagged as theoretically the "correct" fix but impractical at this change's cost budget.

**Decision (2026-09-03): neither candidate is being pursued right now.** Weighing the two ranked candidates against `cascade-eig-calibration`'s own Part 1 vs. Part 2 results changed the calculus: Part 1's large bias numbers (hundreds of bits, interior bucket) turned out to be largely an artifact of an idealized region far bigger than any real board (sized to accommodate the BFS's 500-node cap on an *unbounded* plane; the actual Beginner board is 9x9=81 cells total) — not representative of what a real player sees. Part 2 (real solver-guided games on the actual presets) is the more reliable signal, and its bias is already fairly small (mostly single digits, several deciles under 1 bit, two deciles even slightly *negative*). Against that small a real-world gap, candidate 1 risks overcorrecting into a net underestimate (it would likely be fit against Part 1's stronger, cheaper-to-generate but less-representative signal) and candidate 2 carries real, uncushioned derivation risk (a wrong hand-derived formula has no calibration-harness safety net the way a fitted parameter does). Both stay recorded above as the state of the art if this is revisited, but the next check (see Migration Plan) is a baseline (pre-cascade-aware) comparison on the same Part 2 methodology, to settle the more fundamental question first: does the cascade-aware term help at all, enough to justify keeping it over a plain revert to single-reveal EIG.

## Migration Plan

No data migration - this is a pure computation change in a client-side solver with no persisted state. Ship as a normal change: update `frontierSolver.ts`, update any test fixtures asserting old single-reveal `eig` values, ship. Rollback is a plain revert.

**Planned post-implementation quantification (not part of this change's tasks, tracked separately per user request):** compare `predictedEig` against `revealedInformation` (`revealFeedback.ts`) before and after this change, across real play, to see how much the gap actually closes in practice and how often the fusion blind spot (a cascade reconnecting into another component) shows up as a large residual.

An offline synthetic calibration (generating many random boards at swept mine densities, running real `floodReveal` cascades, and comparing against what the formula would have predicted from the same `(q, d)` inputs) was considered as a way to directly quantify the expected overestimation bias in isolation from real-play noise, and to check whether it's worst near the ~0.1 mine-density transition as theory predicts. Deliberately deferred, not adopted, for now — real predicted-vs-realized numbers from actual play come first; the offline calibration can be revisited afterward if those numbers warrant a closer look at the estimator itself. (That offline calibration was later built as `cascade-eig-calibration`; see its own change and the Risks/Trade-offs updates above.)

**Keep-vs-revert measurement (2026-09-03, `cascade-eig-calibration`'s Part 2 harness extended with a baseline field):** with the two bias-correction candidates deferred (Decision above), the more fundamental question was checked first: does the cascade-aware term actually improve the predicted-vs-realized readout over plain pre-cascade `EIG_single`, for the same real solver-guided moves? `cascadePart2.ts`'s `Part2Move` gained a `baselinePredictedEig` field (`computeSingleRevealEig` on the identical pre-reveal board/cell already used for the shipped `predictedEig`), so both formulas are compared against the identical realized move rather than two separately-played, differently-guided games. Run across 5 independent seed ranges (10 games/preset each, 1291 total recorded moves spanning all 3 presets):

```
                rawBias   ratioBias    MAE      RMSE
cascade-aware   +2.42     2.31         4.08     7.51
baseline        -2.06     0.62         2.29     6.68
```

Signed bias alone looked roughly symmetric (cascade-aware over by ~2.4, baseline under by ~2.1) - consistent with the original goal of "closing a gap that was under, by adding a term." But **mean absolute error is the more literal measure of the proposal's own stated goal** ("close (not eliminate) that gap" between `predictedEig` and `revealedInformation`), and by that measure the cascade-aware term makes the typical prediction *worse*, not better: baseline's MAE (2.29) is ~44% lower than cascade-aware's (4.08), and its RMSE is also lower (6.68 vs 7.51). This held consistently across all 5 independently-seeded runs before pooling (individual-run MAEs: cascade-aware 3.07-4.97, baseline 1.57-3.24 - baseline lower in every single run, no exceptions).

**Reading this alongside the "large Part 1 numbers are largely an idealized-region artifact" finding above:** Part 2's real-play numbers are the trustworthy signal for both questions this document now answers - they're what showed the remaining bias-correction candidates weren't worth pursuing (too small a gap to safely correct without risking overcorrection), and they're what now shows the cascade-aware term itself, as currently implemented, isn't earning its complexity: it turns a smaller (in MAE terms), understated gap into a larger, overstated one. This is a genuine, if unwelcome, empirical result, not a implementation bug (the `p(n)` cap fix, task 2.4, is applied and doesn't materially change this picture per its own measured impact) - it reflects the independence-assumption overestimation risk (above) being large enough in practice to outweigh the value of crediting cascade information at all, at least with this specific single-pass BFS estimator. **This is a strong signal to revert `cascade-aware-eig` back to plain single-reveal EIG** (`EIG_single`, already exposed for testing via `computeSingleRevealEig`) rather than keep the cascade-aware term as shipped - recorded here as a finding; the actual revert is a separate decision/change, not executed as part of this measurement.

- Whether the UI should show `expectedCascadeInfo`/`cascadeProbability` as a visible breakdown next to `eig` (since it's the approximate part) or leave `eig` as a single blended number — this only affects `information-visualization`, a capability this change doesn't otherwise touch, so it can be decided when/if that capability is revisited.
- Whether to pursue a bias-correction follow-up change at all, and if so which of the two candidates the correction-technique literature review (Risks/Trade-offs, above) ranked as viable: an empirically-calibrated local motif/Bonferroni-shaped correction fit against `cascade-eig-calibration`'s harness, or a hand-derived hypergeometric-style entropy correction. Not decided here — this change's own scope (per the calibration change's proposal) is measurement, not correction.
