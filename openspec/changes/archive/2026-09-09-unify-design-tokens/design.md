## Context

See proposal.md — Why.

Two constraints shape the approach:

- **Two consumers with different needs.** The canvas renderer needs color values as JavaScript strings at draw time (`ctx.fillStyle = ...`). The prose pages need them as CSS custom properties. Neither can consume the other's native form directly.
- **The existing palette has provenance.** `probabilityColor.ts` documents its poles, neutral midpoint, EIG ramp, and highlight colors as specific slots from the dataviz skill's `references/palette.md`, with a recorded reason for each (e.g. slot 6 green for premises because slot 5 magenta read too close to the mine-pole red). That reasoning is an asset. This change relocates those values; it does not re-pick them.

## Goals / Non-Goals

**Goals:**

- One place to change a color, with the CSS derived from it rather than maintained alongside it.
- Semantic token names, so `boardRenderer` and the explainer's prose refer to the same concept rather than the same hex string.
- Leave the game page ready for `port-game-ui-to-solid` to consume classes rather than invent them.

**Non-Goals:**

- Re-designing the palette. Every reconciled stray adopts an existing token; no new color is introduced.
- Typography, spacing, and layout tokens. Color is the axis where the duplication actually bites; widening scope here would delay both dependent changes.
- Dark mode.
- Removing `main.ts`'s inline styles (see proposal.md — Impact).

## Decisions

### 1. TypeScript module is the source of truth; the CSS is generated by a build-tool-agnostic script

`src/design/tokens.ts` exports the canonical values. `scripts/generate-tokens.mjs` — roughly ten lines of plain Node — reads it and writes `src/design/tokens.css` as a `:root` block of custom properties. The script runs from `predev` and `prebuild`. The generated file is committed, so a fresh clone works without a build step, and a Vitest test asserts the committed file matches what the generator would produce right now (the same shape as the existing `explanationSnapshot` test).

Two properties make this the right shape here:

- **Drift is structurally impossible**, not merely detected. There is one representation and one derivation of it.
- **It is not coupled to a build tool.** A plain Node script invoked from an npm script survives `migrate-explainer-to-astro-mdx` untouched, because nothing about it knows whether Vite or Astro is running the build.

It also makes tokens the third instance of a pattern the repo already relies on — illustrations and quoted figure values are both generated from real code rather than transcribed — so this is consistent with the codebase rather than novel in it.

*Alternatives considered:*

- **Hand-author the CSS, enforce with a parity test.** The initial choice in this design, on the reasoning that generating would require a custom Vite plugin that the Astro migration would then have to port. That reasoning was wrong: generation needs no plugin, only a script. Setting that aside, a parity test *detects* drift and then asks a human to fix it by hand, where generation removes the possibility. Rejected once the plugin objection disappeared.
- **CSS as source of truth, JS reads via `getComputedStyle`.** Rejected: the canvas can draw before stylesheets resolve, and it makes `probabilityColor` untestable under Vitest's Node environment, where there is no computed style to read. The existing colour tests would have to be rewritten around a DOM.
- **An off-the-shelf token pipeline** — Style Dictionary, Panda CSS, Vanilla Extract, StyleX, `vite-plugin-css-export`. Surveyed against current docs and npm. Vanilla Extract is disqualified outright: `createGlobalTheme` returns `var(--token)` references to JS, and `mixHex()` needs the literal `"#0d366b"` to parse into RGB channels. Tailwind v4 and UnoCSS invert the direction, making CSS the source. Style Dictionary and Panda CSS both genuinely satisfy the two-consumer requirement, and both were rejected on scale: this project has ~14 unique tokens, so the generated artifact is ~14 lines of CSS, and either tool costs more configuration than the file it produces. Panda additionally brings an atomic-CSS framework and a `styled-system/` codegen directory into a project that has no other use for one.

The trade-off to accept: a committed generated file can be stale in a working tree if someone edits `tokens.ts` without running the script. The freshness test is what makes that safe, so it is a required part of this change, not an optional extra.

### 2. Semantic names, not literal ones

Tokens are named for meaning (`safe`, `mine`, `eig`, `clue`, `premise`, `ink`, `surface`, `page`, `rule`), never for appearance (`blue`, `red`). This is what makes the cross-page guarantee meaningful: the explainer's `.term-safe` span and the board's safe-pole cell fill are the same token because they mean the same thing, not because they happen to match.

The existing `:root` block in `explainer.html` already uses this convention, and `probabilityColor.ts`'s constants (`SAFE_POLE`, `MINE_POLE`, `CLUE_HIGHLIGHT`, `PREMISE_HIGHLIGHT`) already agree with it. The token set is largely a formalization of a naming scheme both files independently arrived at.

### 3. Reconciling strays: adopt, don't invent

Each unowned literal maps onto an existing token rather than becoming a new one:

| current | location | token |
|---|---|---|
| `#2b6cb0` | chart series stroke | `safe` |
| `#e74c3c`, `#c0392b` | revealed-mine fill | `mine` |
| `#7f8c8d` | flagged fill | neutral ramp (dim) |
| `#95a5a6` | unknown-probability fill | neutral ramp (mid) |
| `#1a1a1a` | grid labels, cell numbers | `ink` |

`#e74c3c` → `mine` is the one worth naming: the revealed-mine fill and the `p=1` heatmap pole currently differ by a shade for no recorded reason, and both mean "there is a mine here."

The two grays need care. `NEUTRAL_MIDPOINT` (`#c0c0c0`) is load-bearing — it is the diverging scale's `p=0.5` midpoint, and `information-visualization`'s "Maximally uncertain cell shows the neutral midpoint color" scenario depends on it. The flagged and unknown fills must stay visually distinct from it, or a flagged cell reads as a maximally uncertain one. They therefore become their own ramp steps, not aliases of the midpoint.

### 4. The game page's classes land here; `main.ts` consumes them later

This change writes the game page's stylesheet and class names but leaves `main.ts` setting inline styles. That is a deliberate seam, not an oversight: `port-game-ui-to-solid` replaces `main.ts` entirely, and having it emit `class="toolbar"` against a stylesheet that already exists is strictly less work than editing inline styles here and then deleting them there.

Consequence to accept: between these two changes landing, the game page carries both a stylesheet and inline styles, and the inline ones win. The intermediate state is not the finished design.

## Risks / Trade-offs

- **Visual regression on the reconciled colors, with no automated way to catch it** → Four fills change on screen. The test suite asserts that the generated CSS is *current*, not that anything looks right, and this environment has no headless browser, so nothing here can confirm the page still looks right. Mitigation: treat human review of both pages as a required step of this change, and land the reconciliations as their own commit so they can be reverted independently of the token extraction.
- **The committed `tokens.css` goes stale relative to `tokens.ts`** → Someone edits the token module and does not rerun the generator, so the working tree disagrees with itself. The freshness test is the entire mitigation, which makes it load-bearing: it must regenerate in memory and compare against the committed file byte-for-byte, not merely check that the values it can find agree. Wiring the generator into `predev`/`prebuild` means the ordinary workflow fixes this before the test ever fires.
- **A token rename ripples into the explainer's prose styles** → `.term-safe`, `.term-mine`, `.term-clue`, `.term-premise` and the `--eig` callout border already reference these by name in `explainer.html`. Renaming during extraction would touch both files at once. Mitigation: keep the existing names as-is; this change adds a source of truth, it does not rename.
- **Scope creep into a full design system** → Spacing, type scale, and radii are duplicated between the two pages too. Deliberately out of scope; revisit after `migrate-explainer-to-astro-mdx`, when the shared layout makes the right home for them obvious.

## Migration Plan

1. Add `tokens.ts` with values copied verbatim from the two existing sources, plus `scripts/generate-tokens.mjs` and the `predev`/`prebuild` hooks. Commit the generated `tokens.css`. No visible change.
2. Add the freshness test. Confirm it fails when `tokens.ts` is edited without rerunning the generator.
3. Point `probabilityColor.ts` at the tokens. Existing color tests should pass untouched — they assert relationships, not literals.
4. Swap `explainer.html`'s `:root` block for the shared stylesheet. No visible change.
5. Add `index.html`'s stylesheet and game-page classes. No visible change (inline styles still win).
6. Reconcile the strays, as a separate commit. **This is the only step with visible output**; review both pages before continuing.

Rollback: step 6 reverts alone. Steps 1–5 are value-preserving by construction.
