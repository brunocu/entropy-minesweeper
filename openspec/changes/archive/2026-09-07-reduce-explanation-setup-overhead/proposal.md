## Why

`optimize-explanation-extraction` reduced `computeExplanations`' oracle-call count (QuickXplain + a subset-verdict cache) and its own measured results now show that oracle calls were never the dominant cost. On its worst-case board (Intermediate seed 15, move 10) oracle recomputations fell 37% (202 -> 128) while that move's explain time fell only 7% (18.2ms -> 16.9ms) - so roughly four fifths of that move's cost is work the change did not touch. The Beginner row makes the same point from the other direction: a 9x9 board, where `enumerateComponent`'s exponential path essentially never runs, still spends 14.7x `solve`'s time in `computeExplanations` (1.39ms per move) and improved least of all three difficulties (-9.5%, versus -20.8% on Expert). That gradient - biggest win where the CSP is hardest, smallest win where it is trivial - is the signature of a fixed per-certain-cell setup cost that does not scale with CSP difficulty, and it contradicts that change's stated conclusion that "the remaining gap is dominated by the uncapped exponential enumeration on large ambiguous components." Enumeration owns the multi-second Expert hangs (the 709 moves the harness skips as dangerous); it cannot own the 1.39ms floor on Beginner.

Three concrete sources of that floor are visible by inspection in `src/solver/frontierSolver.ts`, and none of them is the CSP:

1. **The clue-adjacency graph is rebuilt from scratch for every certain cell.** `computeExplanations` passes the whole board's `constraints` into `computeExplanationForCell` (line 734) even though it already computed this component's `relevantConstraints` one scope up (line 709). `computeBfsLayers` then calls `buildClueAdjacency(constraints)` with a byte-identical argument once per certain cell, per component, per call - each time paying an `O(sum of deg^2)` pairwise closure over every clue on the board plus a full `Map<Set>` -> `Map<Array>` copy, to produce the same graph every time.
2. **BFS layers are expanded to exhaustion, then mostly discarded.** `computeBfsLayers` walks the entire component before returning, but `growSufficientSet` stops pulling layers as soon as the accumulated set resolves the cell - typically at layer 1 or 2. Every layer past that is built and thrown away, which defeats the point of an insertion-based grow search.
3. **Every oracle query re-serializes its subset into a canonical string.** `subsetSignature` maps each constraint to a template string with its cell list sorted, sorts the resulting string array, and joins it - on cache *hits* as well as misses. The prior change converted 74 misses into hits on that worst-case board and recovered only 1.3ms, which is consistent with the signature build costing a meaningful fraction of the `applyTrivialDeduction` pass it replaces.

## What Changes

- Pass the component's `relevantConstraints` (already computed) into `computeExplanationForCell` instead of the whole board's `constraints`. BFS from a cell over the clue graph can only ever reach clues in that cell's own frontier component - `computeComponents` unions exactly each constraint's cells, so frontier components *are* the connected components of the "clues share an unrevealed cell" relation - which makes this provably layer-identical while shrinking every downstream graph and subset to component scope. This is a correctness fix, not only a performance one. `frontier-solver`'s "Minimal Certainty Explanation" requirement scopes an explanation to "that cell's frontier-component revealed numbered cells", and today that scoping holds only by coincidence: nothing confines `computeExplanationForCell` to the component it is explaining, and the output stays in-component solely because BFS reach happens to coincide with component membership. Handing the pipeline the component's own clues makes the invariant structural instead of accidental.
- Introduce a per-component index, built once per component per `computeExplanations` call and shared by every certain cell in it: a `cellKey -> clueKeys` map, a dense `clueKey -> integer id` map, and the component's subset-verdict cache. Clue neighbours are derived from that index on demand, so `buildClueAdjacency`'s eager pairwise closure and its `Map<Set>` -> `Map<Array>` materialization stop happening at all.
- Make BFS layers lazy: replace `computeBfsLayers`' eager full walk with a layer-at-a-time walker that `growSufficientSet` pulls from, so layers past the one that first resolves the cell are never constructed. `computeClueBfsLayers` (the test-only full-layering view) drains the walker and keeps its current output.
- Replace `subsetSignature`'s per-constraint string canonicalization with a key built from sorted integer ids off the per-component index, with the component's `flagGivens` serialized once into a per-component key prefix rather than re-serialized on every query.
- Scope the subset-verdict cache per component rather than per call. Subsets drawn from different components are disjoint constraint sets and can never collide, so no cache hit is lost; scoping it per component is what makes `flagGivens` constant within a cache and therefore hoistable out of the key.
- Stage the changes independently and re-run the profiling harness after each, recording a per-stage attribution table. The first three - component-scoped constraints, the on-demand `cluesByCell` index, and lazy layers - land unconditionally: they enforce the component-scoping invariant the spec requires, and their measurements are recorded as attribution, never as a gate. Only the last two, the component-scoped cache and the id-based subset keys, are contingent on the measurements justifying their added complexity.
- Amend `optimize-explanation-extraction/design.md` with a dated addendum correcting its "remaining gap is dominated by the uncapped exponential enumeration" conclusion, leaving its original table and reasoning intact.
- The acceptance standard for output is the one `optimize-explanation-extraction` used, not a stricter one: each explanation must be provably correct - irreducible, sufficient, and drawn only from its own frontier component, per `frontier-solver`'s "Minimal Certainty Explanation" requirement - and deterministic for a fixed board state. Byte-identity with today's output is *expected* from every fix here, because each is argued to be output-preserving, but it is a tripwire rather than a requirement: a difference means the argument or the code is wrong and must be diagnosed, and if diagnosis shows a genuine tie between equally-minimal explanations, the fixture is updated and the change proceeds.

## Impact

- `src/solver/frontierSolver.ts`: `buildClueAdjacency` is replaced by a per-component `byCell` index; `computeBfsLayers` becomes a lazy layer walker; `subsetSignature` is replaced by an id-based subset key; `SubsetVerdictCache` moves from call-scoped to component-scoped; `computeExplanationForCell`, `growSufficientSet`, `quickXplain`, and `extractPremiseKeys` all take the per-component index in place of loose `constraints`/`flagGivens`/cache arguments.
- `src/solver/frontierSolver.test.ts`: the test-only exports added by `optimize-explanation-extraction` (`computeSubsetSignatureForTest`, `createSubsetVerdictCacheForTest`, `resolveSubsetForTest`, `quickXplainForTest`, `computeCellExplanationForTest`) change shape, since a subset key is now meaningful only relative to a component index. Their assertions are carried over to the new shape, including the "different givens produce a different key" property.
- `src/explainer/fixtures.test.ts` and `explainer.md`: expected to need no changes, since every fix here is argued to preserve output. A fixture that does move is a signal to diagnose, not an automatic failure - if the cause is a genuine equally-minimal tie the fixture is updated, matching how `optimize-explanation-extraction` handled its QuickXplain tie-breaks.
- No changes to `src/game/gameController.ts`, `src/main.ts`, or any consumer-facing API. `ComponentCache` and `latestExplanations` are untouched.
